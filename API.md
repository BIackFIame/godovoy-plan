# Локальный API «Годового плана» v1

API работает внутри запущенного приложения. Откройте **Интеграции**, выберите порт и нажмите **Включить API**. Защищённый порт по умолчанию — 43857 на 127.0.0.1. Настройка сохраняется в одном локальном профиле. На остальных компьютерах она задаётся отдельно.

Комплектный клиент `godovoy-bridge --request` устанавливает соединение Noise и проверяет подлинность приложения до передачи пути и данных. Ключ используется в рукопожатии. В аргументы команды и JSON его передавать не требуется. Основной токен позволяет читать календарь и создавать события. Токен импорта работает только с `PUT /v1/imports/{source}`. В профиле один токен импорта для всех имён источников. Кнопка **Сменить токены** отзывает оба старых токена. Операция записи сверяет токен и проверяет, включён ли API, под блокировкой профиля перед изменением календаря. При выключении незавершённые соединения закрываются, порт освобождается. Если соединение прервалось до ответа, повторите `PUT` с теми же внешними ID. Повторный `POST` может создать второе событие.

API слушает только IPv4 loopback. Он подходит для программ и скриптов на том же компьютере. Для источника на другом сервере запустите локальный мост. Мост делает исходящий запрос к источнику и передаёт данные приложению по защищённому соединению через loopback. Опубликовать API как внешнюю точку приёма вебхуков в приложении нельзя.

## Методы

| Метод | Адрес | Результат |
| --- | --- | --- |
| GET | `/v1/health` | `{"version":1,"status":"ok"}` с основным токеном |
| GET | `/v1/capacity` | Записи и байты профиля с основным токеном |
| GET | `/v1/members` | Участники с полями `id`, `name` и `revoked` |
| GET | `/v1/events?year=2026&limit=100&offset=0` | События года по возрастанию даты. По умолчанию текущий год и 100 записей, максимум 200 за запрос |
| GET | `/v1/events/{id}?year=2026` | Одно событие и состояние на выбранный год |
| POST | `/v1/events` | Новое событие, код 201. Повтор POST создаёт ещё одно событие |
| PUT | `/v1/imports/{source}` | Импорт или обновление по внешнему ID, с повторным вызовом без дублей |

Чтение события возвращает его UUID, дату и год, название, описание, категорию, признак ежегодного повтора, UUID ответственного, дату начала подготовки, пункты со сроками и отметками, дневник этого года и внешний источник при наличии.

Метод `GET /v1/capacity` доступен с версии 0.5.2. Он возвращает `plans`, `planLimit`, `bytes` и `byteLimit` по последнему сохранённому снимку. `plans` включает историю удалений. Если импорт добавит больше записей, чем умещается, пачка отклоняется целиком с кодом 422. Обновление существующих событий возможно в пределах лимита байтов.

С 0.5.26 `byteLimit` равен 8 МиБ + 64 КиБ. Дополнительное место отведено служебным полям профиля. Данные для сетевого обмена по-прежнему должны помещаться в 8 МиБ. Версии до 0.5.26 могут отказаться открыть файл профиля, если его размер превышает 8 МиБ.

С версии 0.5.33 включение, отключение и смена токенов выполняются в фоне. При отключении окно показывает ход операции. После сохранения отключённого состояния новые запросы теряют доступ, а незавершённые соединения закрываются. Пачки, сохранённые до отключения, остаются в календаре.

Коды ошибок. **401** означает неверный, отозванный или неподходящий токен. **404** означает, что событие отсутствует в запрошенном году. **409** означает, что для чтения ещё нет пространства. **413** означает слишком большой запрос. **422** означает ошибку формы или ограничений хранения. **503** означает, что API выключен или временно не может принять запись. JSON-ошибки API содержат поле `error`. Если рукопожатие не удалось или соединение оборвалось, код ответа API может отсутствовать. При потере ответа на POST проверьте календарь перед повтором. Идемпотентные обновления выполняйте через PUT с устойчивым externalId.

## Переход с версии 0.5.40 и более ранних

Остановите прежние задания, обращавшиеся по HTTP. После обновления откройте **Интеграции**, включите API и скопируйте новые ключи. Старые настройки и ранее выданные ключи не дают доступа к новому API. Защищённый клиент получает ключ из окружения `GODOVOY_API_TOKEN`. Замените вызовы curl или прямого HTTP на запуск комплектного клиента. Не передавайте новые ключи старым HTTP-клиентам, в URL или аргументах процесса.

## Примеры

Вызовите клиент из скрипта или приложения. Он выдаёт тело ответа в stdout, диагностические сообщения в stderr и возвращает ненулевой код выхода при ошибке. Для POST и PUT передайте JSON в UTF-8 через stdin. Для основного ключа достаточно метода и пути; для ключа импорта укажите `--import-key`.

```sh
godovoy-bridge --request GET '/v1/events?year=2026'
godovoy-bridge --request POST /v1/events < event.json
godovoy-bridge --request PUT /v1/imports/intranet --import-key < batch.json
```

Пример содержимого `event.json`:

```json
{
  "title": "Новогодние поздравления",
  "date": "2026-12-20",
  "category": "Partners",
  "yearly": true,
  "preparationDays": 45,
  "checklist": [
    {"key": "contacts", "title": "Обновить список партнёров", "daysBefore": 35}
  ]
}
```

Для назначения выберите участника с `revoked: false` из `GET /v1/members` и передайте его `ownerId`, чтобы у ответственного появился личный чек-лист. Даты передаются в формате `YYYY-MM-DD` без часового пояса. Категории — `Campaign`, `Partners`, `Team`, `Operations`. Максимум 100 пунктов на событие, 4 000 символов для описания. `daysBefore` не превышает `preparationDays`. Ключи пунктов стабильны и уникальны внутри события.

Список участников сохраняет `id` и `name` для отображения истории. У отозванного устройства `revoked` равно `true`. Новое назначение такому участнику возвращает 422. При повторном импорте сохранённый ответственный остаётся в событии, если поле пропущено или повторяет прежний ID. Для переназначения передайте ID действующего участника.

## Импорт с сервера

Мост `godovoy-bridge` идёт в комплекте с приложением. Он запускается отдельным процессом, читает источник по HTTPS и подключается к тому же локальному порту через Noise. Мост проверяет подлинность API по токену импорта до передачи календаря. Используйте мост и приложение версии 0.5 или новее. Для других программ комплектный клиент предоставляет режим одиночного запроса. Укажите в окружении процесса:

- `GODOVOY_API_TOKEN` — токен импорта.
- `GODOVOY_SOURCE_URL` — адрес источника. URL с секретом вебхука тоже храните как секрет.
- `GODOVOY_SOURCE_TOKEN` — Bearer-токен источника, если тот его требует. У него отдельное назначение и адресат.

```sh
./godovoy-bridge --source intranet --format json --every-seconds 900
```

В Windows запускайте `godovoy-bridge.exe`. В комплекте macOS файл находится в `GodovoyPlan.app/Contents/MacOS/`. Без `--every-seconds` мост делает один проход и завершается. При нестандартном порте укажите `--api-port`. Источник получает GET-запрос без учётных данных календаря. Перенаправления и прокси из окружения отключены. Доверие HTTPS задаёт хранилище сертификатов ОС. HTTP допускается для локальных тестовых источников с адресом `127.0.0.1` или `::1`.

### Произвольная система и Neactor

Подготовьте выдачу JSON в таком формате. Эту же структуру можно отправить вручную в `PUT /v1/imports/intranet` с токеном импорта.

```json
{
  "events": [
    {
      "externalId": "process-173",
      "event": {
        "title": "Весенняя акция",
        "date": "2027-04-10",
        "category": "Campaign",
        "description": "План на весну",
        "preparationDays": 30
      }
    }
  ]
}
```

`source` обозначает конкретную учётную запись или сервер. Используйте разные имена для разных систем. `externalId` — неизменный ID события в этой системе. Для Neactor укажите адрес метода чтения нужных записей в `GODOVOY_SOURCE_URL`. Файл `--mapping` задаёт пути к полям вашей формы в ответе, поэтому преобразование работает в самом локальном мосте. Пути записываются в формате JSON Pointer. Например, конфигурация ниже подходит для ответа с массивом `result.items` и вложенным объектом `fields`. Названия и пути здесь условные. Возьмите их из фактического ответа вашей формы. [API Neactor](https://developers.neaktor.com/) · [Отправка POST из Neactor](https://neaktor.com/support/otpravit-post-zapros)

```json
{
  "items": "/result/items",
  "id": "/id",
  "title": "/fields/name",
  "date": "/fields/plannedDate",
  "description": "/fields/description",
  "category": "Operations",
  "auth": "bearer"
}
```

```sh
./godovoy-bridge --source neactor-office --mapping neactor.json --every-seconds 900
```

Поле `items` может быть пустой строкой для массива в корне. `id`, `title`, `date` и `description` отсчитываются от отдельной записи. Дата может быть строкой `YYYY-MM-DD`, `ДД.ММ.ГГГГ` или отметкой времени, начинающейся с такой даты. В сопоставлении также доступны постоянные `category`, `preparationDays` и `yearly`. Для метода чтения через POST добавьте `postBody` с JSON-фильтром. `auth` поддерживает `bearer`, `authorizationRaw` и `xApiKey`. Значение токена задаётся через окружение. Мост обрабатывает один ответ за проход. Если источник выдаёт данные страницами, настройте диапазон в URL или фильтре запроса.

Файл сопоставления ограничен 64 КиБ. С версии 0.5.32 при ошибке разбора мост сообщает строку и столбец без содержимого поля.

### Bitrix24

Для календаря компании укажите в `GODOVOY_SOURCE_URL` полный URL метода `calendar.event.get` входящего вебхука с правом `calendar`. Мост делает POST к Bitrix24 и переносит ID, название, дату и доступное описание. Назначение ответственного и расширенные правила повторения Bitrix24 остаются в источнике. Такие события можно дополнять в локальном календаре. [Метод calendar.event.get](https://apidocs.bitrix24.com/api-reference/calendar/calendar-event/calendar-event-get.html)

```sh
./godovoy-bridge --source bitrix-office --format bitrix-calendar \
  --from 2026-01-01 --to 2027-12-31 --every-seconds 900
```

Без `--from` и `--to` мост при каждом запросе берёт текущий локальный календарный год. Если указать хотя бы одну границу, диапазон фиксируется при запуске. Пропущенная граница соответствует началу или концу года запуска.

### Правила обновления

- Одна пара `source` + `externalId` соответствует одному локальному UUID. Повтор неизменного импорта возвращает `changed: false`.
- Если источник не передаёт необязательные поля, уже заданные ответственный, категория, описание, подготовка и чек-лист сохраняются. Явное пустое описание или пустой список пунктов их очищают. Для ручной смены ответственного используйте редактор.
- Изменение названия пункта с тем же `key` сохраняет его отметку. У ежегодного события дневник, отметки и правки «только на этот год» относятся к отдельному году.
- С 0.5.23 при переносе одноразового импортированного события через Новый год сохраняются UUID, дневник и последние отметки, включая правки коллег офлайн. При конкурирующих переносах клиенты выбирают дату по ревизии. Для `GET` используйте год актуальной даты. Для ежегодного повтора уже переносившегося разового события используйте новый внешний ID.
- Формат хранения и обмена остаётся прежним. Клиенты до 0.5.23 могут показывать историю только за запрошенный год или видеть обе даты после конкурирующих переносов. Для единого отображения обновите все рабочие места.
- Отсутствие записи в очередной выгрузке не удаляет событие. Для ежегодного шаблона перенос базовой даты в другой календарный год требует нового внешнего ID. Запрос принимает до 100 событий и 512 КиБ. Каждая пачка фиксируется целиком. Мост делит крупную выдачу на пачки и может повторить импорт после ошибки.

Машиночитаемое описание находится в [openapi.yaml](openapi.yaml).

### Результаты импорта в приложении

В **Интеграциях → Журнал импорта** видны последняя принятая пачка и последний отказ для каждого недавнего источника на этом компьютере. У принятой пачки указано число полученных и изменённых событий. У отказа показывается категория причины. Источник задаёт клиент в имени маршрута или `--source`.

С версии 0.5.25 приложение и мост дополнительно показывают итог последнего прохода, в том числе пустую выгрузку и ошибку внешнего источника. При частичном импорте счётчики учитывают только пачки, по которым пришло подтверждение. Если ответ потерян, приложение сообщает, что последняя пачка могла сохраниться. Вывод моста остаётся доступен, если локальный API не смог получить сводку.

Сводка использует отдельное зашифрованное сообщение на прежнем локальном порту и отправляется после завершения прохода. Мост и приложение предыдущих версий продолжают обмениваться пачками. Запросы с недействующим токеном и неразобранным телом в журнал не записываются.

Хранятся результаты 32 последних источников. В `imports-v1.json` сохраняются метка, время, счётчики, категория отказа и идентификаторы локального профиля. Записи истории остаются на этом компьютере. При частых одинаковых отказах или пачках без изменений время в окне обновляется сразу. Повторная запись таких результатов на диск выполняется при следующей пачке после интервала в 30 секунд.

Итоги моста находятся в отдельном `bridge-runs-v1.json` с таким же лимитом в 32 источника. Файл содержит время получения, заданную клиентом метку, тип результата и счётчики. URL, токены, содержимое событий и текст ошибок в сводке отсутствуют.
