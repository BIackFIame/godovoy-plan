# Резервные копии календаря в 0.5.6

Копию создают в разделе **Календарь → Резервные копии**. Файлы сохраняются в папке `backups` внутри профиля. Для хранения на другом диске подходит копия всей папки вместе с `origin.json`. Окно восстановления показывает до 32 последних копий. [Создание копии](backup-created.png)

Восстановление доступно в календаре и на экране ошибки запуска. Перед подтверждением видна дата копии. Приложение проверяет структуру и принадлежность копии, закрывает фоновые процессы и открывает профиль под исключительной блокировкой. Если прежний `calendar.json` существует, его файл сохраняется отдельно в той же папке, а замена записывается атомарно. Профиль с сохранёнными копиями при отсутствии `calendar.json` сразу открывает экран восстановления. [Подтверждение восстановления](backup-confirm.png)

Копия содержит идентификатор устройства и ключ синхронизации команды. Токены API и подтверждения одноразовых приглашений исключаются. При откате исправного календаря остаются текущие настройки интеграций, токены и счётчик версий. При восстановлении повреждённого профиля API нужно включить заново. Файл отметок о прочтении хранится отдельно в профиле.

Сразу после восстановления обмен с коллегами на паузе. При его возобновлении более свежие правки коллег могут вернуться. Действующие интеграции исправного профиля могут продолжить импорт.

В нативном окне macOS с временным профилем прошли создание копии, отмена и восстановление повреждённого календаря. Проверены неизменность исходного файла после отмены, отдельное хранение его байтов после восстановления и запуск синхронизации на паузе. Все 39 тестов Rust прошли, включая отказ от чужой или повреждённой копии и попытку восстановления при занятом профиле. Форматирование и Clippy с запретом предупреждений прошли.

Windows x86, x64 и ARM64 собраны кросс-компиляцией. Проверка восстановления в Windows остаётся открытой.

## Пауза после перезапуска в 0.5.12

В 0.5.11 пауза после восстановления действовала до закрытия приложения. В 0.5.12 её состояние записывается вместе с восстановленным профилем, до запуска фонового обмена. Если запись при отключении паузы завершается ошибкой, обмен остаётся приостановлен, а приложение показывает ошибку в окне «Синхронизация». Ручная пауза использует ту же настройку профиля. Действующие интеграции по-прежнему управляются отдельно.

В нативном окне macOS проверены создание копии, отмена восстановления, восстановление повреждённого файла, запуск с сохранённой паузой и явное включение обмена через флажок. Последующие запуски сохранили выбранный режим в обе стороны. Регрессионный тест воспроизвёл сбой на 0.5.11, а в 0.5.12 дополнительно подтвердил, что ошибка записи профиля оставляет обмен на паузе. Все 46 тестов Rust прошли.

## Повреждённая копия при открытом календаре в 0.5.13

В 0.5.12 при подтверждении восстановления приложение закрывало открытый календарь перед проверкой копии. Повреждённая копия оставляла сотрудника на экране восстановления, а локальный API переставал отвечать. В 0.5.13 восстановление из окна календаря использует уже открытую эксклюзивную блокировку. При ошибке сотрудник видит сообщение о выбранной копии и может вернуться к открытому календарю кнопкой **Отмена**. После успешной записи приложение подхватывает восстановленный календарь с сохранённой паузой обмена.

На временных профилях в нативном окне macOS воспроизвели сбой 0.5.12 и проверили обе ветки 0.5.13. Пока была видна ошибка повреждённой копии, локальный `/v1/health` возвращал HTTP 200, основной файл сохранил прежние байты, а **Отмена** вернула к календарю. Применение исправной копии вернуло данные из неё, сохранило прежний файл отдельно, открыло локальный API с текущими настройками и поставило обмен на паузу. Тест Rust подтвердил, что блокировка профиля остаётся у приложения и снимок публикуется после записи. Всего прошли 47 тестов Rust.

## Прерывание записи в 0.5.14

На macOS сравнили диагностические сборки 0.5.13 и 0.5.14. Для каждой завершили дочерний процесс `SIGKILL` в 11 точках записи календаря, создания копии и восстановления. До атомарной замены предыдущий `calendar.json` оставался побайтно прежним. После замены следующий процесс открывал изменённый или восстановленный календарь с ожидаемым содержимым всех 500 событий. При восстановлении существующего файла проверили отдельно сохранённые байты оригинала и паузу обмена. Готовые копии пережили прерывание создания новой копии. [Результаты по этапам](crash-matrix.json)

В шести сценариях на диске оставался промежуточный файл. 0.5.14 убрала все такие файлы после открытия исправного календаря. Для уборки предназначены обычные файлы с зарезервированным именем `.godovoy-stage-` и 16 буквенно-цифровыми знаками. Старые `.tmp*`, сохранённые оригиналы и содержимое повреждённого профиля при неудачном открытии остаются доступны.

Отдельный прогон подтвердил, что прерванный первый запуск можно повторить. После удаления уже созданного календаря без копий 0.5.13 записывала новый пустой профиль, а 0.5.14 оставила `calendar.json` отсутствующим и сообщила об ошибке. Для старого профиля защита вступает в силу после первого открытия в 0.5.14. Все 49 тестов Rust прошли. Отключение питания и Windows в этот эксперимент не входили.

## Последняя копия и восстановление открытого календаря в 0.5.22

Окно читает список при открытии и сразу обновляет строку даты после создания копии. Содержимое проверяется при восстановлении.

Если `calendar.json` повреждён или отсутствует при открытом приложении, восстановление сохраняет рабочее состояние в файл `calendar-open-before-restore-*.json` в закрытой папке профиля. Существующий повреждённый файл остаётся отдельно под именем `calendar-before-restore-*.json`. Окно показывает пути. Рабочий снимок включает текущие настройки, поэтому храните его в той же защищённой папке. После восстановления открытого календаря действующие токены и счётчик версий сохранены, синхронизация на паузе. При восстановлении после неудачного запуска токены из копии не возвращаются.

Нативный тест macOS проверил пустой список, создание копии и отображение той же даты после повторного запуска. Тест Rust отдельно сравнил сохранённый рабочий снимок и байты повреждённого файла, а после восстановления проверил календарь на диске, текущие токены, счётчик версий и паузу синхронизации. Сценарии использовали временные профили.

## Возврат из окна восстановления в 0.5.27

Перед заменой приложение сохраняет пригодный календарь как отдельную точку возврата в папке `backups`. В списке восстановления видны до 32 ручных копий и до 32 точек возврата. При выборе точки текущий календарь тоже сохраняется. В точку входят данные и ключ команды. Токены API и регистрации приглашений исключены, действующие настройки исправного профиля сохраняются при восстановлении.

Если копии доступны только для чтения, восстановление продолжается после сохранения прежних данных в отдельный файл. Приложение сообщает об отсутствии точки возврата. Если жёсткую ссылку для предыдущего файла создать не удалось, приложение пробует ограниченное копирование его исходных байтов. Если сохранить прежний файл невозможно, основной календарь остаётся прежним.

Нативная проверка macOS прошла восстановление ручной копии, возврат через точку и восстановление повреждённого файла через список. Пауза сохранилась после запуска, старые токены не активировались, повреждённые байты сохранились отдельно. После проверки окна исправили обрезку текста и кнопок на размере 600 × 470.

## Подтверждение возврата в 0.5.34

Из результата восстановления кнопка **Вернуть прежний календарь…** ведёт к подтверждению именно созданной точки возврата. Если точка исчезла, приложение показывает список доступных копий с пояснением. Исходные файлы раскрываются отдельно. Предупреждение о ключе команды и токенах видно до раскрытия. Основное окно показывает имя каждого из этих файлов и даёт скопировать его полный путь.

В нативном окне macOS 1040 × 630 проверили профиль с длинным путём, повреждённым файлом на диске и исправным календарём в памяти. До раскрытия были видны предупреждение, возврат и закрытие. После раскрытия помещались обе строки файлов и кнопки. Прямой возврат открыл подтверждение нужной точки и восстановил исходное содержание календаря. Отдельное подтверждение после ошибки запуска проверено при 600 × 470. Синтетические токены остались в полном рабочем снимке, а точки возврата очищены от токенов. Повреждённые байты сохранились побайтно. Прошли 118 Rust-тестов и Clippy.

## Результат восстановления в 0.5.35

Результат восстановления сообщает, что календарь открыт и синхронизация на паузе. **Готово** закрывает результат. **Вернуть прежний календарь…** открывает подтверждение возврата. Список копий называет сохранённое прежнее состояние **Точка возврата**. Создание резервных копий доступно в отдельном окне календаря.

Повторный прогон macOS на синтетическом профиле подтвердил, что при 1040 × 630 предупреждение и обе кнопки видны до раскрытия сведений. После раскрытия помещаются оба файла с кнопками копирования пути. Проверены возврат к прежнему календарю, сохранение паузы после перезапуска и восстановление повреждённого календаря при 600 × 470.

## Фоновое восстановление в 0.5.36

После подтверждения фоновый поток проверяет копию, сохраняет оригинал и заменяет календарь. При запросе закрытия окно ждёт завершения, а при ошибке остаётся открытым. Кнопка **Остаться в приложении** отменяет только закрытие окна. После успеха LAN-обмен остаётся на паузе.

При восстановлении со стартового экрана открытый профиль получает ту же файловую блокировку, которая удерживалась при записи. Уже проверенный календарь используется при открытии без повторного чтения файла.

## Запись копии в 0.5.37

Копия получает снимок и время под блокировкой календаря. Сериализация и запись проходят в фоне после снятия этой блокировки. Новые изменения продолжают записываться в текущий календарь. Из резервной копии по-прежнему исключены токены API и выданные приглашения.

Диалог копий можно закрыть во время записи. Результат появится внизу рабочей вкладки, а подробная ошибка останется в «Резервных копиях». Запрос на закрытие приложения ждёт завершения записи. Если запись завершилась ошибкой, окно остаётся открытым.
