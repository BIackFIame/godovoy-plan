# API серверного календаря

Интеграция обращается к тому же HTTPS-имени, что и браузер. Для локального теста подойдёт `http://127.0.0.1:45838`. Для каждого запроса нужен заголовок `Authorization: Bearer <ключ>`. Выдайте отдельный ключ на интеграцию. Для отчётов используйте `grant --read-only`. Ключ редактора с общей видимостью может читать и изменять события всей команды. Для обработки только назначенных интеграции событий включите персональную область в карточке её сотрудника в локальной консоли ИТ. Храните ключ в закрытом хранилище интеграции, отключите журналирование заголовка и тел запросов.

При доступе извне нужны разрешение внешнего входа в политике узла и ключ интеграции с флагом `--allow-remote`. На внешнем входе действующий офисный ключ получит HTTP 403 для проверки сеанса, запроса календаря и изменения событий. Выдавайте такое право отдельно для каждой интеграции, которой требуется доступ из-за пределов офиса. [Настройка двух входов](ONLINE.md#один-календарь-для-офиса-и-удалённых-сотрудников)

На офисном резервном узле успешный ответ защищённого API содержит `x-godovoy-standby-until` — время окончания окна в секундах Unix (UTC). Закрытое окно даёт 503 и `x-godovoy-standby: unavailable` после проверки ключа. При отказе хранилища возможен обычный 503. При потере подтверждения записи проверьте состояние после восстановления. [Развёртывание сервера](SERVER.md)

| Запрос | Результат |
|---|---|
| `GET /v1/session` | 204 при действующем доступе. Пустой ответ. |
| `GET /v1/state?year=2027` | JSON с полями `workspaceName`, `employeeId`, `employees`, `canEdit`, `assignedOnly`, `allowFreeText`, `year`, `events`, `tasks`. Массив `events` относится к указанному году (1900–9999), `tasks` — к текущим задачам владельца ключа. |
| `POST /v1/command` | JSON с полем `op`. Заголовок `Content-Type: application/json`. По умолчанию успешное сохранение возвращает 204. Для обновлённого состояния снова прочтите год. |

### Повторное чтение открытого года

С версии 0.5.49 ответ `200 OK` на `GET /v1/state` содержит `ETag`. Пока этот год открыт под тем же ключом, отправляйте полученную метку в `If-None-Match`. Если отображаемые данные прежние, ответ будет `304 Not Modified` без тела. Сервер заново проверит ключ, область доступа, настройки организации и срок резерва, а также учтёт текущую дату для напоминаний. При изменении отображаемых данных ответит `200` со свежим JSON и меткой.

При сохранении отметки `check` или записи `note` клиент может передать метку своего открытого года в `X-Godovoy-Base` и год в `X-Godovoy-Year`. Если эта метка совпала с предыдущим состоянием под тем же ключом, ответ `200 OK` содержит JSON с полями `id`, `year`, `events`, `tasks` и заголовок `X-Godovoy-State-Tag` с новой меткой. В каждом из двух списков удалите все строки события с этим `id`, затем последовательно вставьте каждую полученную строку `event` на позицию `index` (счёт с нуля). Применяйте ответ только к исходной версии открытого года. Если получен `204`, изменение сохранено: запросите год снова, чтобы учесть изменения коллег. Клиенты без поддержки этого режима продолжают получать `204`.

Для условного чтения после работы коллеги можно добавить заголовок `X-Godovoy-Delta: event-v1` к `GET /v1/state` с одной точной меткой в `If-None-Match`. Ответ `304` сохраняет текущий экран. У полного `200` по-прежнему есть `ETag` и все поля года. У компактного `200` есть `X-Godovoy-Delta-Base` с меткой исходного экрана и `X-Godovoy-State-Tag` с меткой восстановленного года. Тело содержит те же `id`, `year`, `events` и `tasks`, что и подтверждение записи. После проверки обеих меток, года, структуры и позиций строк обновите оба списка вместе. Если экран уже сменился или полученный ответ несовместим, запросите полный год без условных заголовков.

Сервер хранит в памяти одно подтверждённое изменение после записи `check` или `note` с квитанцией. Для каждого читателя он заново проверяет доступ и строит его представление. Две пропущенные записи, другой контекст доступа и изменение календаря сторонней программой могут потребовать полного ответа. Повторное открытие приложения и работа без поддержки этого заголовка используют обычный протокол `200/304`.


Храните метку в памяти вместе с соответствующим ответом. При смене ключа, года или после блокировки экрана сбросьте её. Если подключение прервалось или проверка доступа завершилась ошибкой, закройте прежнее отображение. Режим `Cache-Control: no-store` действует и для условных ответов. Клиенты без метки получают прежний полный ответ. Повторный запрос года по-прежнему регистрируется в журнале.

### Видимость и изменение прав

В 0.5.46 каждый успешный ответ трёх запросов выше содержит `x-godovoy-assigned-only` и `x-godovoy-allow-free-text` со строковым значением `true` или `false`. В JSON-состоянии соответствующие поля имеют логический тип. После изменения любого признака очистите прежнее отображение и заново запросите состояние. Для статуса доступа достаточно пустого ответа `GET /v1/session`. Данные, которые интеграция уже перенесла в собственную систему, требуют отдельного управления доступом.

| Правило | Ответ сервера и разрешённые действия |
|---|---|
| `assignedOnly=false` | В `events` доступен календарь команды за выбранный год. В `employees` перечислены сотрудники с действующими ключами. Редактор может работать с шаблонами. |
| `assignedOnly=true` | В `events` и `tasks` доступны только собственные назначения, в `employees` — строка вошедшего сотрудника. Сервер проверяет владельца конкретного события и года при каждой записи. Редактору доступны `check` и разрешённая политикой `note`. |
| `canEdit=false` | Все операции записи запрещены, включая отметки и заметки. |
| `allowFreeText=false` | В событиях обеих выдач `description` и `note` возвращаются пустыми строками. Не отправляйте непустое описание и команды `note`, в том числе с пустым текстом. При доступном `editEvent` пустое или пропущенное `description` сохраняет прежний скрытый текст. |

Для HTTP 403 считывайте заголовок `x-godovoy-access`, если он есть. После запрета показа прекратите выдачу ранее загруженного календаря с прежней областью.

| `x-godovoy-access` | Причина и действие |
|---|---|
| `office-only` | Для внешнего входа использован действующий офисный ключ. Подключитесь через разрешённый офисный маршрут. |
| `remote-disabled` | Администратор закрыл внешний вход для всех ключей. Проверьте настройки перед повтором. |
| `assigned-only` | Операция с шаблоном либо целевым событием недоступна в персональной области. Чужая и неизвестная цель получают одинаковый отказ. Обновите состояние. |
| `free-text-disabled` | Узел отклонил описание или операцию с дневником по политике. Обновите видимые поля и состояние. |

При отказе с ключом «только чтение» или при отклонении источника запроса заголовок может отсутствовать. Отключение внешнего входа и отзыв ключа проверяются для чтения, записи и проверки сеанса. Административная консоль запускается отдельной командой на локальном порту. Ключи интеграций дают доступ только к пользовательскому API. [Консоль ИТ](ONLINE.md#локальная-консоль-ит)

### Подключение ИИ

Сервер 0.5.47 принимает MCP-запросы по пути `/mcp`. Для него выдаётся отдельный ключ, привязанный к сотруднику. Его нельзя использовать на маршрутах `/v1`. [Инструкция и перечень инструментов](MCP.md)

### Команды календаря

Пример тела для создания ежегодной задачи со сроком подготовки за 45 дней до события:

```json
{
  "op": "createEvent",
  "title": "Поздравить партнёров",
  "description": "",
  "category": "Partners",
  "date": "2027-12-20",
  "yearly": true,
  "ownerId": null,
  "preparationDays": 45,
  "checklist": [{"title": "Согласовать текст", "daysBefore": 21}]
}
```

Чтобы назначить ответственного, подставьте UUID из `employees[].id`. Категории — `Campaign`, `Partners`, `Team`, `Operations`. В каждом событии возвращаются его ID и год, поля календаря, даты подготовки, чек-лист с ID, сроками и отметками, заметка `note` и версия `revision`.

| Команда | Обязательные данные и поведение |
|---|---|
| `editEvent` | `eventId`, `year`, `revision`, `scope` и полный набор полей события как при создании. Сохраняйте ID прежних пунктов чек-листа. |
| `deleteEvent` | `eventId`, `year`, `revision`, `scope`. Область `year` действует на один год, `future` — с этого года вперёд. |
| `check` | `eventId`, `year`, `taskId`, `done` (логическое значение). |
| `note` | `eventId`, `year`, `text`, `base` (предыдущий текст из состояния). |

При HTTP 429 подождите не менее указанного в `Retry-After` числа секунд. Сервер ещё не принимал команду к выполнению. При 401 приостановите интеграцию и проверьте ключ. При 403 проверьте права и адрес. При 409 перечитайте событие и покажите конфликт до повторной записи. При 400, 413, 415 или 422 исправьте запрос. При 503 проверьте доступность узла, диска и журнала. При потере ответа на создание сначала сверьтесь с календарём. Автоматический повтор может создать дубликат.

Данные, полученные внешней системой, попадают под её правила доступа, хранения и удаления. Отзыв ключа блокирует будущие запросы. [Настройка узла и восстановление](ONLINE.md) · [Отдельный API локального профиля](API.md)
