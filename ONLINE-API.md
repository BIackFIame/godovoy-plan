# API серверного календаря

Интеграция обращается к тому же HTTPS-имени, что и браузер. Для локального теста подойдёт `http://127.0.0.1:45838`. Для каждого запроса нужен заголовок `Authorization: Bearer <ключ>`. Выдайте отдельный ключ на интеграцию. Для отчётов используйте `grant --read-only`. Ключ редактора с общей видимостью может читать и изменять события всей команды. Для обработки только назначенных интеграции событий включите персональную область в карточке её сотрудника в локальной консоли ИТ. Храните ключ в закрытом хранилище интеграции, отключите журналирование заголовка и тел запросов.

При доступе извне нужны разрешение внешнего входа в политике узла и ключ интеграции с флагом `--allow-remote`. На внешнем входе действующий офисный ключ получит HTTP 403 для проверки сеанса, запроса календаря и изменения событий. Выдавайте такое право отдельно для каждой интеграции, которой требуется доступ из-за пределов офиса. [Настройка двух входов](ONLINE.md#один-календарь-для-офиса-и-удалённых-сотрудников)

На офисном резервном узле успешный ответ защищённого API содержит `x-godovoy-standby-until` — время окончания окна в секундах Unix (UTC). Закрытое окно даёт 503 и `x-godovoy-standby: unavailable` после проверки ключа. При отказе хранилища возможен обычный 503. При потере подтверждения записи проверьте состояние после восстановления. [Развёртывание сервера](SERVER.md)

| Запрос | Результат |
|---|---|
| `GET /v1/session` | 204 при действующем доступе. Пустой ответ. Заголовок `X-Godovoy-Can-Edit` сообщает актуальное право записи (`true` или `false`). |
| `GET /v1/state?year=2027` | JSON с полями `workspaceName`, `employeeId`, `employees`, `canEdit`, `assignedOnly`, `allowFreeText`, `year`, `events`, `tasks`. Массив `events` относится к указанному году (1900–9999), `tasks` — к текущим задачам владельца ключа. |
| `POST /v1/command` | JSON с полем `op`. Заголовок `Content-Type: application/json`. По умолчанию успешное сохранение возвращает 204. Для обновлённого состояния снова прочтите год. |

### Проверка версии после медленной загрузки

Для проверки уже полученного ответа отправьте `HEAD /v1/state?year=…` с тем же личным ключом, форматом строк и заголовком `If-None-Match` с меткой полного снимка. Используйте `X-Godovoy-State-Tag`, если сервер его прислал, иначе `ETag`. Оставьте запрос без `X-Godovoy-Delta` и `X-Godovoy-Page`. Сервер заново проверяет права и актуальную версию этого года. Совпадение даёт 304. При другой доступной версии вернётся 200. Оба ответа на HEAD приходят без тела. Отказ в доступе требует очистить загруженные данные.

Штатный веб-клиент использует эту проверку, когда чтение выходит за 4,5 секунды от начала запроса, и перед показом полного списка по кнопке «Показать ещё». Он ждёт заголовки до 4,5 секунды, версионированное тело календаря — до 45 секунд с момента заголовков. При смене версии повторяет чтение один раз с тем же форматом выдачи. Тайм-аут отдельной проверки и операций записи остаётся 4,5 секунды.

### Повторное чтение открытого года

С версии 0.5.49 ответ `200 OK` на `GET /v1/state` содержит `ETag`. Пока этот год открыт под тем же ключом, отправляйте полученную метку в `If-None-Match`. Если отображаемые данные прежние, ответ будет `304 Not Modified` без тела. Сервер заново проверит ключ, область доступа, настройки организации и срок резерва, а также учтёт текущую дату для напоминаний. При изменении отображаемых данных ответит `200` со свежим JSON и меткой.

При сохранении отметки `check` или записи `note` клиент может передать метку своего открытого года в `X-Godovoy-Base` и год в `X-Godovoy-Year`. Если эта метка совпала с предыдущим состоянием под тем же ключом, ответ `200 OK` содержит JSON с полями `id`, `year`, `events`, `tasks` и заголовок `X-Godovoy-State-Tag` с новой меткой. В каждом из двух списков удалите все строки события с этим `id`, затем последовательно вставьте каждую полученную строку `event` на позицию `index` (счёт с нуля). Применяйте ответ только к исходной версии открытого года. Ответ `204` подтверждает сохранение, в том числе когда сервер не смог подготовить обновлённое представление. Запросите год снова, чтобы учесть изменения коллег. Клиенты без поддержки этого режима продолжают получать `204`.

Успешный ответ `200` на чтение года для редактора с заголовком `X-Godovoy-Personal-Check: assigned-v1` подтверждает поддержку проверки `onlyIfAssigned`.

Если после отметки клиент остаётся в списке, он может добавить к запросу квитанции заголовок `X-Godovoy-Receipt: rows-only-v1`. В квитанции сводки придут изменения строк без дополнительной карточки `detail`.

### Уведомление об изменении открытого года

Добавьте заголовок `X-Godovoy-Watch-Year: 2028` к запросу `GET /v1/state?year=2028`. Укажите год экрана. Если узел поддерживает наблюдение и располагает свободным местом, в ответе придёт `X-Godovoy-Watch`. Сохраните его в оперативной памяти вместе с версией прочитанного года. По тому же ключу отправляйте год и в обычной проверке `GET /v1/session`.

Изменение значения в успешном ответе означает, что стоит перечитать отображаемый год с его `ETag`. При исчезновении ранее полученного заголовка перечитайте год один раз. Такое бывает после перезапуска или при смене версии узла. Учитывайте новое значение после применения данных к экрану. Значение непрозрачно и привязано к ключу, году и действующим правам. Источником данных и подтверждением доступа остаётся обычное авторизованное чтение.

Этот сигнал охватывает видимые данному сотруднику изменения чек-листов и дневника через веб-команды и MCP того же процесса. Сохраняйте периодическое условное чтение для изменений через другой вход, внешние интеграции и старые серверы. При `401` или `403` очистите закрытые данные и прекратите использование метки.

### Получение изменившегося события

Для условного чтения после работы коллеги можно добавить заголовок `X-Godovoy-Delta: event-v1` к `GET /v1/state` с одной точной меткой в `If-None-Match`. Ответ `304` сохраняет текущий экран. У полного `200` по-прежнему есть `ETag` и все поля года. У компактного `200` есть `X-Godovoy-Delta-Base` с меткой исходного экрана и `X-Godovoy-State-Tag` с меткой восстановленного года. Тело содержит те же `id`, `year`, `events` и `tasks`, что и подтверждение записи. После проверки обеих меток, года, структуры и позиций строк обновите оба списка вместе. Если экран уже сменился или полученный ответ несовместим, запросите полный год без условных заголовков.

Сервер хранит в памяти одно подтверждённое изменение после записи `check` или `note` с квитанцией. Для каждого читателя он заново проверяет доступ и строит его представление. Две пропущенные записи, другой контекст доступа и изменение календаря сторонней программой могут потребовать полного ответа. Повторное открытие приложения и работа без поддержки этого заголовка используют обычный протокол `200/304`.

### Сводка года и полная карточка

Веб-клиент может явно предложить `X-Godovoy-View: overview-v1` для `GET /v1/state`. Для сотрудника с доступом ко всему календарю сводка включается, когда в выбранном году видны как минимум 80 событий. На внешней точке входа клиент с форматом строк `tuple-v2` также получает сводку при 128 и более пунктах в чек-листах этого года. Сервер возвращает `overview: true`, счётчики `completed` и `total` и ближайший открытый пункт `next` в личных задачах. Описания, дневник и полный чек-лист отсутствуют. Без отметки `overview` сохраняется прежняя форма ответа. У сводки со всеми событиями `ETag` и `X-Godovoy-State-Tag` содержат одну сильную метку. Повторяйте заголовок `X-Godovoy-View` при условном чтении и записи `check` или `note`. В компактной квитанции записи может быть `detail` с одной обновлённой карточкой.

Для компактной передачи списка клиент может добавить заголовок `X-Godovoy-Rows: tuple-v2` к запросу сводки. Если сервер возвращает `rowFormat: "tuple-v2"`, каждый элемент `events` и `tasks` содержит ровно девять значений в порядке `[id, year, title, date, category, ownerRef, completed, total, next]`. В поле ownerRef целое число обозначает позицию сотрудника в массиве employees этого же ответа, начиная с нуля. Для прежнего ответственного вне списка передаётся строка UUID. Ссылку следует раскрыть перед обработкой изменений отдельных событий. Отсутствующий владелец и ближайшая задача передаются как JSON `null`. При наличии ближайшей задачи последнее значение содержит объект с полями `id`, `title`, `dueDate`. Если `rowFormat` отсутствует, используйте обычные именованные поля. Повторяйте выбранный заголовок при условном чтении, открытии карточки и записи с квитанцией. Полная карточка и изменения отдельных событий сохраняют именованные поля. Метка компактной сводки привязана к её формату и текущим правам.


Для открытия строки используйте `GET /v1/event?year=ГОД_ЭКРАНА&eventYear=ГОД_СОБЫТИЯ&id=UUID` с одним точным `If-Match` со значением `X-Godovoy-State-Tag` сводки. Сервер заново проверяет права, состояние выбранного года и видимость строки. Успешный JSON содержит прежнюю полную структуру карточки и `X-Godovoy-State-Tag`. При `412` обновите год и повторно проверьте наличие строки. При `404` строка отсутствует в разрешённом представлении. Все ответы для этих маршрутов имеют `Cache-Control: no-store`.

### Компактные карточки календаря

Если клиент понимает tuple-v2 для сводки, он может также отправлять `X-Godovoy-Cards: tuple-v1` при чтении, открытии карточки и записи с квитанцией. Используйте одни и те же заголовки для всего сеанса. Сервер сохраняет обычные пороги выбора сводки и прежний набор разрешённых полей.

Если небольшой календарь уже получает полные карточки, ответ может содержать `cardFormat: "tuple-v1"`. Каждый элемент `events` тогда содержит по порядку `id, year, title, description, category, date, yearly, ownerId, preparationDays, preparationDate, checklist, note, revision`. Каждый пункт чек-листа содержит `id, title, daysBefore, dueDate, done`. В `tasks` неотрицательное целое указывает индекс той же карточки в `events` этого ответа. Задача из другого года, которой нет в `events`, содержит полный кортеж. Для ограниченного сотрудника при наличии карточек `assignedOwnerId` соответствует разрешённому владельцу. У полного компактного ответа собственная метка. Сохраняйте её вместе с декодированным представлением. При отсутствии `cardFormat` применяйте обычный формат ответа.

Если календарь использует сводку, отдельный `GET /v1/event` всё так же требуется при открытии карточки и проверяет полную метку выбранного снимка. Этот маршрут возвращает обычный объект карточки. Квитанции записи сохраняют свой согласованный формат.

### Страницы сводки

Клиент может добавить `X-Godovoy-Page: first-v1` вместе с `X-Godovoy-View: overview-v1` и `X-Godovoy-Rows: tuple-v2`. При доступе ко всему календарю с более чем 80 событиями `events` содержит первые 80 событий в порядке даты и идентификатора, `eventCount` — общее число событий выбранного года, а `tasks` — все текущие личные задачи, включая задачи других лет. В этом ответе `ETag` относится к странице, а `X-Godovoy-State-Tag` — к полному снимку. Если `eventCount` отсутствует, получены все строки. Это относится и к внешнему календарю с 80 или меньшим числом событий, который уже перешёл на сводку из-за объёма чек-листов.

Размеры годовой части сводки ограничены согласованными значениями `first-v1` (80), `prefix-160-v1`, `prefix-320-v1`, `prefix-640-v1` и `prefix-1280-v1`. Чтобы получить остальную часть года, опустите заголовок `X-Godovoy-Page`. Каждое частичное представление имеет собственный `ETag`. Полная сводка всегда включает все личные задачи. Ответ на частичную сводку без `eventCount` также содержит весь разрешённый год.

Внешний слушатель возвращает `X-Godovoy-Continuations: v1` в ответе на первую частичную сводку. Веб-клиент выбирает продолжение для медленной передачи по длительности и размеру уже загруженной страницы. Решение действует только в памяти этого сеанса.

Для продолжения уже загруженной страницы передайте в GET следующую ступень через `X-Godovoy-Page`, предыдущую ступень через `X-Godovoy-Continue` и точную метку предыдущей страницы через `X-Godovoy-Base`. Когда следующая ступень покрывает остаток года, опустите `X-Godovoy-Page`. Определите вид ответа по заголовкам.

- При совпадении версии и разрешений `X-Godovoy-Continued` повторяет метку предыдущей страницы. JSON содержит `year`, `offset`, `eventCount` и массив `events` только с новыми годовыми строками. Эти строки используют формат tuple-v2 и список сотрудников ранее проверенного снимка. `ETag` относится к телу продолжения. `X-Godovoy-State-Tag` подтверждает версию полного календаря, а `X-Godovoy-Page-Tag` даёт метку объединённой страницы, пока в году остались строки.
- При изменении версии, формата или разрешений сервер повторно проверяет доступ и может вернуть обычную разрешённую сводку. Прежние серверы также могут прислать весь год. Обрабатывайте такой ответ как самостоятельный снимок, заменяя предыдущие данные.
- Перед показом догрузки выполните `HEAD` того же года без заголовков страницы и продолжения. Передайте метку полного снимка в `If-None-Match` и проверьте ответ 304, текущий режим доступа, активный год и сеанс. На время сетевого ожидания продолжает действовать исходный срок доступа. При изменившемся снимке заново загрузите разрешённый список.

- Для условного обновления страницы повторите все три заголовка и передайте её `ETag` в `If-None-Match`. Сервер вернёт `304` или новый снимок страницы вместе с личными задачами. Для сводки со всеми событиями доступен протокол `event-v1`.
- Для уже открытой страницы можно добавить `X-Godovoy-Delta: page-event-v1`. Если коллега изменил одну отметку или заметку у видимой строки, сервер может прислать только сводку этой строки и соответствующие личные строки. `X-Godovoy-Delta-Base` должен совпадать с сохранённой меткой именно этой страницы. Проверьте год, идентификатор, состав и позиции строк, затем вместе примените списки, новую метку страницы из `X-Godovoy-Page-Tag` и новую метку полного снимка из `X-Godovoy-State-Tag`. Если ответ несовместим, перечитайте страницу без условной метки. При изменении состава или порядка событий, пропущенных правках и изменении прав сервер возвращает актуальную разрешённую страницу или отказ в доступе.
- Для карточки используйте `X-Godovoy-State-Tag` в `If-Match`. Для записи с квитанцией используйте ту же метку в `X-Godovoy-Base` и повторите три заголовка. Успешная квитанция обновляет обе метки. `X-Godovoy-State-Tag` — новая метка полного снимка, `X-Godovoy-Page-Tag` — новая метка страницы. В её `events` могут измениться только строки запрошенной страницы, а в `tasks` — соответствующие личные строки. Для карточки и этих записей достаточно первой страницы.
- Для показа остальных событий заново прочтите год с заголовками сводки и формата строк, опустив `X-Godovoy-Page` и условный заголовок. Полученный полный список заменяет страницу после проверки его метки через HEAD. Если за время загрузки изменились права, сбросьте прежнее отображение.

Храните метку в памяти вместе с соответствующим ответом. При смене ключа, года или после блокировки экрана сбросьте её. Если подключение прервалось или проверка доступа завершилась ошибкой, закройте прежнее отображение. Режим `Cache-Control: no-store` действует и для условных ответов. Клиенты без метки получают прежний полный ответ. Повторный запрос года по-прежнему регистрируется в журнале.

### Сводка назначенных событий

Клиент с режимом «Только назначенные события» может предложить `X-Godovoy-Assigned-View: overview-v1` вместе с `X-Godovoy-View: overview-v1` и `X-Godovoy-Rows: tuple-v2`. Сервер отправляет сводку, когда в выбранном году у сотрудника не менее 80 событий или суммарно не менее 128 пунктов в их чек-листах. Сводка включает все разрешённые годовые строки и личные задачи, в том числе задачи других лет. Для этого режима заголовок `X-Godovoy-Page` не ограничивает список. Если сервер вернул полный ответ, продолжайте использовать вложенные карточки.

Поле `assignedOwnerId` в сводке задаёт канонический идентификатор владельца назначений. У сотрудника со старым идентификатором устройства он может отличаться от `employeeId`. После раскрытия `ownerRef` у всех строк событий и личных задач должен быть этот владелец. В сводку входят только данные, доступные запросившему сотруднику. Политика свободного текста, право записи и проверка назначения для каждой команды действуют и при работе со сводкой.

Повторяйте `X-Godovoy-Assigned-View` при условном чтении, запросе карточки и записи с квитанцией. Используйте `X-Godovoy-State-Tag` для `If-Match` карточки и `X-Godovoy-Base` записи. Веб-клиент перед показом карточки подтверждает эту же метку запросом HEAD с заголовками сводки. Изменение назначения требует свежего чтения. При отказе в доступе закрывается и список, и открытая карточка.

### Видимость и изменение прав

В 0.5.46 каждый успешный ответ трёх запросов выше содержит `x-godovoy-assigned-only` и `x-godovoy-allow-free-text` со строковым значением `true` или `false`. В JSON-состоянии соответствующие поля имеют логический тип. После изменения любого признака очистите прежнее отображение и заново запросите состояние. Для статуса доступа достаточно пустого ответа `GET /v1/session`. Данные, которые интеграция уже перенесла в собственную систему, требуют отдельного управления доступом.

| Правило | Ответ сервера и разрешённые действия |
|---|---|
| `assignedOnly=false` | В `events` доступен календарь команды за выбранный год. В `employees` перечислены сотрудники с действующими ключами. Редактор может работать с шаблонами. |
| `assignedOnly=true` | В `events` и `tasks` доступны только собственные назначения, в `employees` — строка вошедшего сотрудника. Сервер проверяет владельца конкретного события и года при каждой записи. Редактору доступны `check` и разрешённая политикой `note`. |
| `canEdit=false` | Все операции записи запрещены, включая отметки и заметки. |
| `allowFreeText=false` | В событиях обеих выдач `description` и `note` возвращаются пустыми строками. Не отправляйте непустое описание и команды `note`, в том числе с пустым текстом. При доступном `editEvent` пустое или пропущенное `description` сохраняет прежний скрытый текст. |

Для HTTP 403 считывайте заголовок `x-godovoy-access`, если он есть. После запрета показа прекратите выдачу ранее загруженного календаря с прежней областью.

| `x-godovoy-access` | Причина и действие |
|---|---|
| `office-only` | Для внешнего входа использован действующий офисный ключ. Подключитесь через разрешённый офисный маршрут. |
| `remote-disabled` | Администратор закрыл внешний вход для всех ключей. Проверьте настройки перед повтором. |
| `assigned-only` | Операция с шаблоном либо целевым событием недоступна в персональной области. Чужая и неизвестная цель получают одинаковый отказ. Обновите состояние. |
| `free-text-disabled` | Узел отклонил описание или операцию с дневником по политике. Обновите видимые поля и состояние. |

При отказе с ключом «только чтение» или при отклонении источника запроса заголовок может отсутствовать. Отключение внешнего входа и отзыв ключа проверяются для чтения, записи и проверки сеанса. Административная консоль запускается отдельной командой на локальном порту. Ключи интеграций дают доступ только к пользовательскому API. [Консоль ИТ](ONLINE.md#локальная-консоль-ит)

### Подключение ИИ

Сервер 0.5.47 принимает MCP-запросы по пути `/mcp`. Для него выдаётся отдельный ключ, привязанный к сотруднику. Его нельзя использовать на маршрутах `/v1`. [Инструкция и перечень инструментов](MCP.md)

### Команды календаря

Пример тела для создания ежегодной задачи со сроком подготовки за 45 дней до события:

```json
{
  "op": "createEvent",
  "title": "Поздравить партнёров",
  "description": "",
  "category": "Partners",
  "date": "2027-12-20",
  "yearly": true,
  "ownerId": null,
  "preparationDays": 45,
  "checklist": [{"title": "Согласовать текст", "daysBefore": 21}]
}
```

Чтобы назначить ответственного, подставьте UUID из `employees[].id`. Категории — `Campaign`, `Partners`, `Team`, `Operations`. В каждом событии возвращаются его ID и год, поля календаря, даты подготовки, чек-лист с ID, сроками и отметками, заметка `note` и версия `revision`.

| Команда | Обязательные данные и поведение |
|---|---|
| `editEvent` | `eventId`, `year`, `revision`, `scope` и полный набор полей события как при создании. Сохраняйте ID прежних пунктов чек-листа. |
| `deleteEvent` | `eventId`, `year`, `revision`, `scope`. Область `year` действует на один год, `future` — с этого года вперёд. |
| `check` | `eventId`, `year`, `taskId`, `done` (логическое значение). При `onlyIfAssigned: true` сервер перед записью проверяет, что событие всё ещё назначено сотруднику, чей ключ использован. Для сотрудника с общей видимостью устаревшее назначение даёт `409`. |
| `note` | `eventId`, `year`, `text`, `base` (предыдущий текст из состояния). |

При HTTP 429 подождите не менее указанного в `Retry-After` числа секунд. Сервер ещё не принимал команду к выполнению. При 401 приостановите интеграцию и проверьте ключ. При 403 проверьте права и адрес. При 409 перечитайте событие и покажите конфликт до повторной записи. При 400, 413, 415 или 422 исправьте запрос. При 503 проверьте доступность узла, диска и журнала. При потере ответа на создание сначала сверьтесь с календарём. Автоматический повтор может создать дубликат.

Данные, полученные внешней системой, попадают под её правила доступа, хранения и удаления. Отзыв ключа блокирует будущие запросы. [Настройка узла и восстановление](ONLINE.md) · [Отдельный API локального профиля](API.md)
