# API серверного календаря

Интеграция обращается к тому же HTTPS-имени, что и браузер. Для локального теста подойдёт `http://127.0.0.1:45838`. Для каждого запроса нужен заголовок `Authorization: Bearer <ключ>`. Выдайте отдельный ключ на интеграцию. Для отчётов используйте `grant --read-only`. Все допущенные клиенты видят весь календарь. При наличии права записи интеграция может изменять события всей команды. Храните ключ в закрытом хранилище интеграции, отключите журналирование заголовка и тел запросов.

| Запрос | Результат |
|---|---|
| `GET /v1/session` | 204 при действующем доступе. Пустой ответ. |
| `GET /v1/state?year=2027` | JSON с полями `workspaceName`, `employeeId`, `employees`, `canEdit`, `year`, `events`, `tasks`. Массив `events` относится к указанному году (1900–9999), `tasks` — к текущим задачам владельца ключа. |
| `POST /v1/command` | JSON с полем `op`. Заголовок `Content-Type: application/json`. Успешное сохранение возвращает 204. Для обновлённого состояния снова прочтите год. |

Пример тела для создания ежегодной задачи со сроком подготовки за 45 дней до события:

```json
{
  "op": "createEvent",
  "title": "Поздравить партнёров",
  "description": "",
  "category": "Partners",
  "date": "2027-12-20",
  "yearly": true,
  "ownerId": null,
  "preparationDays": 45,
  "checklist": [{"title": "Согласовать текст", "daysBefore": 21}]
}
```

Чтобы назначить ответственного, подставьте UUID из `employees[].id`. Категории — `Campaign`, `Partners`, `Team`, `Operations`. В каждом событии возвращаются его ID и год, поля календаря, даты подготовки, чек-лист с ID, сроками и отметками, заметка `note` и версия `revision`.

| Команда | Обязательные данные и поведение |
|---|---|
| `editEvent` | `eventId`, `year`, `revision`, `scope` и полный набор полей события как при создании. Сохраняйте ID прежних пунктов чек-листа. |
| `deleteEvent` | `eventId`, `year`, `revision`, `scope`. Область `year` действует на один год, `future` — с этого года вперёд. |
| `check` | `eventId`, `year`, `taskId`, `done` (логическое значение). |
| `note` | `eventId`, `year`, `text`, `base` (предыдущий текст из состояния). |

При 401 приостановите интеграцию и проверьте ключ. При 403 проверьте права и адрес. При 409 перечитайте событие и покажите конфликт до повторной записи. При 400, 413, 415 или 422 исправьте запрос. При 503 проверьте доступность узла, диска и журнала. При потере ответа на создание сначала сверьтесь с календарём. Автоматический повтор может создать дубликат.

Данные, полученные внешней системой, попадают под её правила доступа, хранения и удаления. Отзыв ключа блокирует будущие запросы. [Настройка узла и восстановление](ONLINE.md) · [Отдельный API локального профиля](API.md)
